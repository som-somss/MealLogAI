# 내 조합 다시 기록하기·개인 분량·인분 계산 · 2026-11-08

## 구현 범위

홈의 **내 조합 다시 기록하기** 또는 기존 조합 목록에서 저장된 메뉴를 선택합니다. 기록 날짜·시각·끼니를 확인하고 조합 전체 비율, 인분 또는 완성한 음식의 g으로 먹은 양을 계산합니다. 재료별 양 수정과 제외는 이번에 만드는 식사에만 반영합니다. 확인 화면을 거쳐 서버 저장·재조회를 완료해야 성공을 표시합니다.

사용자가 확인한 개인 분량은 기존 `food_memories`에 이름과 함께 저장합니다. 같은 계정의 같은 음식 이름·브랜드·단위에만 선택 버튼을 표시합니다. 분량을 선택한 영양값은 해당 조합의 영양 기준으로 계산합니다. 모든 계란/밥에 일괄 적용하거나 자동으로 식사·조합을 수정하지 않습니다.

`meal_combinations`에 nullable `yield_servings`, `cooked_weight`를 추가했습니다. 기존 조합은 미설정으로 유지합니다. 전체 2인분 중 0.5인분과 완성 무게 800g 중 200g은 모두 25%입니다. 원재료 무게의 합을 완성 무게로 추정하지 않습니다. 재료 변경 시 완성 무게를 지우고 다시 확인하도록 하며, 전체 인분은 유지합니다.

새 SQL 함수 `meallog_record_combination`은 authenticated/security invoker로 실행하고 기존 RLS와 `meal_apply_plan`을 사용합니다. 서버가 저장 조합의 revision과 분모를 확인해 재계산합니다. 요청 ID와 인자를 저장해 동일 요청 재시도는 기존 식사를 반환합니다. 식사가 나중에 편집되거나 삭제됐을 때도 과거 요청을 재적용하지 않습니다. 기기 대기 정보는 사용자별로 분리하고, 계정 변경·화면 닫기 후 늦은 응답을 무시합니다.

- 마이그레이션 `combination_record_portions` 적용. `tests/combination-record-db.sql`을 authenticated 역할 및 현재 초기화 세대 헤더로 트랜잭션 실행한 뒤 **ROLLBACK**. 인분/g/재료별 계산, 동일 요청 재시도, 타인 조합·분량 쓰기 차단, 잘못된 인자 무변경, revision 충돌, 조합 변경 시 완성 무게 초기화, 과거 식사 보존, 기존 식사 편집 후 재시도, 불명 영양 보존을 확인했습니다.
- 로그인된 검증 주소에서 별도 합성 조합(전체 2인분/800g)을 사용했습니다. 0.5인분 → 밥 100g + 계란 25g, **179kcal**가 새 식사로 저장되고 DB의 비율 0.25 및 음식 JSON과 일치했습니다.
- 같은 화면에서 합성 계란의 ‘한 알 = 50g’을 저장하고 선택했을 때 **228kcal**로 재계산됨을 확인했습니다. 새로고침 후 기억 버튼을 다시 조회했고, 전체 분량 설정의 revision 증가 및 200g/800g 계산도 확인했습니다.
- 모바일 360px에서 중첩 스크롤을 없애고 조합 제목·닫기 버튼이 보이게 수정했습니다. 새로고침 직후 동기화 안내에서 다시 불러오기 버튼으로 복구됨을 확인했습니다.
- 합성 식사·조합·분량·요청·관련 이력만 정리했습니다. 해당 계정의 전체 식사, 기존 조합(새 nullable 컬럼 제외), 기존 개인 분량 JSON 지문이 검증 전과 일치했습니다. 실제 시오콘부볶음밥과 점심 기록을 변경하지 않았습니다.
- Supabase 보안 점검은 전후 동일한 기존 4개 항목이며 새 경고가 없습니다.
- 운영과 동일한 배포를 연결한 로그인 주소에서 기본 조합 402kcal/계란 50g을 다시 읽었습니다. 브라우저 error/warn 및 운영 배포 최근 30분 error/fatal 로그가 없습니다. DB를 직접 사용하는 화면이므로 로그만으로 저장 성공을 판단하지 않았습니다.
